# 客服自动回复质量评估（任务 0109）

把业务方的模糊要求（"准确、有用、语气好、不能瞎编"）变成一套可运行、可复现、可解释的评估流水线：
对 `data/auto_replies.json` 里的 20 条自动回复逐条评分，输出整体得分、各指标分布与最差 3 条分析，
并用 `data/human_ref.json` 的人工标注验证评估方法是否靠谱。

**仓库地址**：https://github.com/chenyimingming/ceping

## 1. 快速开始

### 1.1 环境

- Python 3.10+（本机实测 3.14.6），**零第三方依赖**（只用标准库）。
- 在仓库根目录运行所有命令。

### 1.2 运行

```powershell
# 规则基线：离线、零成本、可复现（不需要 API Key）
python run_eval.py --mode mock

# 真实 LLM 评审（DeepSeek，OpenAI 兼容接口）
copy config.example.json config.json   # 复制配置模板
# 编辑 config.json，把 api_key 换成你的真实 Key（config.json 已被 .gitignore 排除，永不提交）
python run_eval.py --mode llm

# 可选：查询你账号下实际可用的模型名
python run_eval.py --mode llm --list-models

# 可选：每个指标单独调用一次（评分更独立，调用次数约为 4 倍）
python run_eval.py --mode llm --granularity metric
```

### 1.3 输出文件（`outputs/`）

| 文件 | 说明 |
| --- | --- |
| `<mode>_report.md` | Markdown 版报告（整体得分、分布、最差 3 条、一致性校验、缺口清单、20 条明细） |
| `<mode>_report.html` | 单文件 HTML 报告（自带样式，便于截图与部署） |
| `<mode>_report.json` | 完整结构化结果（含每条证据句、理由、能力缺口） |
| `<mode>_scores.csv` | 逐条分数表 |
| `<mode>_console.txt` | 终端输出摘要（截图用） |

### 1.4 配置文件说明（`config.json` / `config.example.json`）

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `base_url` | `https://api.deepseek.com` | OpenAI 兼容接口地址 |
| `model` | `deepseek-flash` | 当前推荐的 DeepSeek 模型名（对应 DeepSeek-V4.1-Flash）；旧名 `deepseek-v4-flash` 服务端仍接受；也可用 `deepseek-v4-pro` |
| `api_key` | 空 | 你的 DeepSeek API Key；**只放本地 `config.json`**，模板 `config.example.json` 不要填真实 Key |
| `temperature` | `0.0` | 温度 0：让评分尽量固定、可复现 |
| `granularity` | `case` | `case`=每条回复一次调用（默认，成本低）；`metric`=每个指标一次调用 |

## 2. 指标定义与选择理由

业务方四个模糊词 → 四个可自动评估的指标（1-5 分，允许 0.5 步进）：

| 业务要求 | 指标 | 量化方式 | 选择理由 |
| --- | --- | --- | --- |
| 准确 | `accuracy` 准确性 | 评审按评分细则打分并给出证据句；规则层同时比对"最小知识库"（如民航局 100Wh 规定、数据集内一致的退款时效口径） | 客服回复的信任底线；可对照人工参考检查冲突 |
| 有用 | `usefulness` 有用性 | 3 个子信号（具体性/行动性/完备性）取均分；区分"通用信息""正确但没用""答非所问" | 本批数据里区分度最高，也是人工标注最集中的批评点（把活推回给用户） |
| 语气好 | `tone` 语气与共情 | 情绪场景评"安抚是否有效、是否甩锅、是否讲内部事项"；中性场景评礼貌专业度 | 可自动评但主观性最强，给低权重并标注置信度 |
| 不能瞎编 | `faithfulness` 忠实性 | 抽取回复中的具体断言（数字/政策/承诺/对用户状态的断言），判断是否有依据；出现无依据断言=`fabrication` 硬门槛 | 低概率、高危害；与"有用性"存在真实冲突（不编造但没帮上忙），必须独立成指标 |

**优先级（业务方问题 5 的答案）**：

1. 第一档硬门槛：忠实性 + 准确性（出现编造或准确性 ≤2 分 → 该条判不合格，综合分封顶 60）；
2. 第二档：有用性；
3. 第三档：语气与共情。

**综合分权重**：忠实性 30% + 准确性 25% + 有用性 30% + 语气 15%（可在 `src/aggregate.py` 调整）。

## 3. 评估方法

### 3.1 流水线结构

```
data/auto_replies.json + data/human_ref.json
        │（合并成 20 条 case）
        ▼
规则层（src/features.py）：情绪/故障/困难、道歉/承接/自助导向/追问/内部事项、数字断言、能力关键词
        ▼
评审层：mock（src/judge_mock.py，确定性规则打分） 或 LLM（src/judge_llm.py，DeepSeek 按同一细则打分）
        ▼
汇总层（src/aggregate.py）：加权综合分 + 硬门槛封顶 + 指标分布 + 最差 3 条
        ▼
校验层（src/validate.py）：与人工信号逐条一致性、排序相关、最差名单重合、锚点用例
        ▼
报告（src/report.py）：outputs/<mode>_report.{json,md,html,csv} + <mode>_console.txt
```

### 3.2 两种口径（能力缺口 vs 质量失分）

- **主口径（能力边界内质量分）**：按 `capabilities.json` 的能力清单打分。系统不具备的能力（如查订单、查物流、查商品参数），
  自动回复"没有执行"不扣分；但回复本可以给出更清晰的路径、更主动的承接、更明确的兜底却未做到时，仍然扣分。
- **严格口径（对照）**：假设系统具备真人客服的全部查询与代办能力，"没有帮用户做本可做的事"要扣分。
- 两套分数的差值 + `capability_needs` 标注，合成"能力缺口清单"（报告第五节），供业务方决定"补哪些系统能力"。
- `capabilities.json` 的取值（具备/不具备/未知）是**从 20 条回复的实际行为与人工标注推导的初始值**（文件内已注明"未经业务方确认"）；
  业务方改这个文件后重跑，评分口径随之变化。

### 3.3 盲评与复现

- **盲评**：提示词只包含"用户问题 + 自动回复 + 能力清单 + 评分细则"，不包含 `human_ref.json` 的人工参考与标注分析，
  避免用人工答案污染评分；人工参考仅用于事后一致性校验。
- **复现**：温度 0；LLM 结果按"模型+温度+完整提示词"的哈希写入 `cache/llm_cache.json`，重复运行不重复计费；
  报告里记录数据指纹（`auto_replies.json` / `human_ref.json` / `human_signals.json` 的 sha256 前 12 位）。
- **mock 与 LLM 的关系**：mock 是零成本基线与无网络兜底；LLM 是主力评审（识别语义类问题）。
  两者输出同一结构，报告可对照。

## 4. 用 human_ref 验证评估方法

1. `data/human_signals.json`：由 `human_ref.json` 的标注分析逐条推导出的人工信号（poor/mixed/good + 关键短语 +
   是否与系统能力相关），**文件内明确标注为推导标签、不参与评分、仅用于校验**。
2. 校验 5 项：
   - 与人工信号的有用性逐条一致率；
   - 综合分与人工粗分的排序相关（Spearman）；
   - 评审"最差 5 条"与人工"差评集合"的重合数；
   - 8 个锚点用例（如 case_08/case_20 的有用性必须低、case_02/03/09/10/18 的准确性必须高）；
   - 能力缺口覆盖（人工标注中与能力相关的 case，是否被"严格口径 vs 能力口径"的差值捕获）。
3. 当前基线（mock）结果：逐条一致 11/20，Spearman 0.519，最差 5 条重合 4/5，锚点 8/8 通过，能力缺口捕获 10/14。
   不一致的 case 会列在报告"与人工信号的一致性"一节，并在第 6 节讨论原因。

## 5. 结果摘要

### 5.1 mock 基线（当前已运行）

- 整体加权分 **84.1 / 100**（严格口径对照 79.6）；不合格 0 条；
- 各指标均值：准确性 5.0｜有用性 2.7｜语气 4.2｜忠实性 5.0；
- 最差 3 条：`case_01`（74.5）、`case_06`（74.5）、`case_05`（77.5）；
- 关键观察：这 20 条里"准确/不瞎编"几乎没有负例（也没有编造），区分度集中在"有用性"——
  大量回复"规则正确，但把该做的事推回给用户"；语气整体良好，个别情绪场景（如 case_07/case_15）力度不足。

### 5.2 LLM 评审（DeepSeek）

运行 `python run_eval.py --mode llm` 后结果写入 `outputs/llm_report.*` 与 `outputs/llm_console.txt`，
其一致性指标会与 mock 基线并列出现在同一份报告结构中，便于对照"规则 vs 语义评审"的差异。

## 6. 局限性（哪些 case 可能评不准）与改进方向

1. **没有业务知识库**：准确性/忠实性只能对照公开口径与数据集内一致性（如退款时效、100Wh 规定），
   商家政策真伪无法独立核验 → 可能放过错误政策，也可能误伤措辞不同但正确的回复。
2. **能力清单是推导值**：主口径分数随能力假设变化；`capabilities.json` 需要业务方确认后再用于正式决策。
3. **LLM 评委的偏差**：偏爱长回答/列表格式、同族模型打分偏松、评分漂移；已用固定细则 + 温度 0 + 缓存 + 证据句缓解，
   但仍建议按比例抽检人工复核。
4. **mock 基线识别不了细粒度语义**：例如 case_20 的"答非所问"、case_17 的"先让用户自助"，
   规则层会漏判或高估（当前一致性 11/20 就反映了这一点）——这正是需要 LLM 评审的原因，mock 只作兜底。
5. **样本太小**：20 条、单一电商客服场景、单轮对话 → 只能给方向性结论，不能给统计显著性或"扩面"的最终决策依据。
6. **语气评分最主观**：本批人工标注对语气只给了少量信号（case_07/case_15），语气指标的校准证据最弱。
7. **看不到最终解决率**：单轮评估无法判断用户问题最终是否解决。

改进方向：

1. 接入业务知识库（政策、商品、订单域）后做事实核验；
2. 建 50~100 条的人工金标集，定期校准评委（含"同分档"边界样例）；
3. 多评委投票/交叉模型评审，降低单模型偏好；
4. 上线后用真实指标回验（转人工率、满意度、复购、投诉率），把评估结果与业务结果对齐；
5. 把流水线接入 CI/定时任务，实现"每次提示词或策略变更自动回归"。

## 7. AI 工具使用情况（如实说明）

1. **开发方式**：本项目的指标设计、代码、测试与报告由 Codex（桌面版）在作者指导下协作完成；
   关键决策（指标口径、能力两栏评法、LLM 模式、推送仓库）由作者拍板，AI 负责落地与验证。
2. **流水线内的 AI**：LLM 评审使用 DeepSeek（OpenAI 兼容接口、JSON 输出模式、温度 0），
   提示词与评分细则集中在 `src/rubric.py`（盲评、两口径、四指标锚点、证据句要求）。
3. **对 AI 产出的验证**：31 项单元测试（`tests/`）、8 个锚点用例、与人工信号的一致性校验、
   每条结论都带证据句与理由，报告中可直接抽查。
4. **离线可用**：mock 模式完全不调用外部服务（无 Key 也能完整跑通）；
   LLM 模式才需要 Key 与网络，且结果有缓存、可复现。

## 8. 目录结构

```
ceping/
├─ run_eval.py               # 命令行入口（mock / llm 两种模式）
├─ config.example.json       # 配置模板（提交）
├─ config.json               # 本地真实配置（含 Key，不提交）
├─ capabilities.json         # 系统能力清单（推导初值，可改后重跑）
├─ data/
│  ├─ auto_replies.json      # 任务数据：20 条自动回复
│  ├─ human_ref.json         # 任务数据：人工参考 + 标注分析
│  ├─ eval_criteria.md       # 任务数据：业务方原始要求
│  └─ human_signals.json     # 由标注推导的人工信号（仅用于校验）
├─ src/                      # 流水线代码（加载/特征/细则/mock/LLM/汇总/校验/报告/配置）
├─ tests/                    # 单元测试与锚点断言
├─ outputs/                  # 评估报告（json/md/html/csv/console.txt）
├─ screenshots/              # 截图与《截图清单.md》
└─ cache/                    # LLM 结果缓存（不提交）
```
